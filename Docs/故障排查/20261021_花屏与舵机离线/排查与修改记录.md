# 2026-10-21 花屏与 STS 离线排查

## 已确认的现场证据

- 用户：复位文字正常，稍后预览区域出现条纹；执行 `@lcd test` 能显示 RGB 三色块和文字。用户已确认 TTL TXD 接 PA3、RXD 接 PA2、共地。
- 用户状态：`CAM ready=1 enabled=1 frames=1 errors=0 timeout=21 loopmax=8`。启动识别成功不等于采集成功。
- ST-Link 热插拔只读连接：STM32H7、Device ID 0x450、Rev V、2 MB Flash、目标电压 3.26 V。初次读取没有停止或复位目标。
- DCMI CWSIZER=0x00EF01DF，对应 480 个字节/行、240 行；DMA2 Stream7 目标 0x24000000。帧缓冲为 DMA 可访问 AXI SRAM。
- `camera_before.bin` 为运行中读取的 115200 字节 RGB565 数据；`camera_before.png` 是其直接还原。还原图也有条纹，因此异常存在于 LCD 输出之前。读取过程中采集仍可能更新，不能据此评价单帧撕裂或准确图像质量。
- 舵机旧日志 `rx` 为 P3 接受的应答数，不是 UART 原始字节数。`pe` 也不是 UART 硬件校验错误；`te` 混合舵机发送与遥测入队错误，不能直接判断线路故障。
- 上游源码 USART2 使用 1000000 baud；保留默认 ID=0。没有把用户记忆中的 9800 当作舵机真实出厂波特率。

## 本次修改

1. OV5640 从厂商自动 PCLK 配置切换为手动分频 4。按原初始化表的 24 MHz 输入、160 MHz 时钟树，对应约 40 MHz，给当前 200 MHz HCLK 和 FPC 留出采样/总线余量。配置集中在 `integration_config.h: BOARD_CAMERA_PCLK_DIV`，只影响 OV5640；DMA 优先级从低改高。是否解决现场异常以板上复验为准。
2. 初始化读回 0x4300/0x501F 格式寄存器及 0x460C/0x3824 时钟寄存器，并检查 SCCB 读错误；不是 RGB565 或分频写入失败时报告失败。
3. 摄像头仅在帧标记、DMA READY、DCMI/DMA 均无错误且 NDTR=0 时显示图像；错误/超时保存 DCMI、DMA 错误和剩余 word 数，`@status` 可见。
4. UART 改速前调用 HAL_UART_AbortReceive，结束旧中断接收，再初始化并重新挂接接收。旧主机测试没有正确覆盖带接收状态的重初始化，本次补充模型。
5. 新增 `rawRx` 原始字节累计、总线 TX 次数、真实 HAL 最近状态及底层解析错误计数，区别“完全没收到”和“收到但无法组包”。
6. 新增 `@servo probe ID BAUD`，只读 PING/READ，ID 0–253、波特率 9600–1000000，ONLINE 时拒绝重探测。识别出非配置 ID 时保持只读，不交给 ID=0 的运动控制层；不修改舵机 ID、EEPROM、扭矩或目标位置。
7. `@lcd test` 先清全屏，避免旧预览残留被误认为仍花屏。

## 复验命令

1. `@status`：OV5640 期望 `format=6F01 pclk=2204`；观察 frames 是否持续增加、timeout 是否继续快速增加。
2. `@lcd test`：关闭预览、清屏、显示 RGB 三色块；`@camera on` 回到实时预览。
3. `@servo probe 0 1000000`，等待约 1 秒后 `@status`。若 rawRx=0，优先检查供电、TTL 电平/适配板及 RX/TX；若 rawRx>0，结合 valid/parser/tx 判断回显、错误 ID、速率或坏帧。
4. 可尝试 `@servo probe 1 1000000`，此命令不会运动，也不会修改设备 ID。若 ID1 在线，要先确认实际设备身份后再调整集中配置。


## 板上复验补记

- 第一次尝试在 HOTPLUG 连接下写入时擦除失败。随后用 NORMAL、950 kHz SWD 重试，得到 `Download verified successfully`，MCU 软件复位成功。没有执行全片擦除、校准区擦除或选项字节修改。
- 手动 8 分频试验：读回 `format=6F01 pclk=2208`，但 `frames=0`、超时 NDTR=28800（整帧未传输），不能作为可用默认值。此试验已撤换，不能把“黑屏不花”当作修复成功。
- 增加 `@camera clock DIV`（0=原自动模式；1/2/4/8/16=手动分频），暂停采集、配置、读回检查后再启动，允许交叉验证而不必反复烧录。正常默认固定为现场验证的 4 分频。
- 运行期切换为 4 分频后，`frames=15` 增长到 `frames=215`；`timeout=13` 保持不变。随后 `@camera off` 冻结，读取 `camera_clock4.bin` 并还原 `camera_clock4.png`，未见原条纹；图像较暗，仍需用户将镜头对准明亮目标验证内容及随动。捕获为非持续写入状态，剩余分条刷新可能被中断，不宣称该截图已验证屏幕整帧显示。
- `@servo probe 1 1000000` 被接受；查询后 `rawRx=0 valid=0 parser=0 tx=114 hal=0`，仍无任何接收字节。已恢复 ID=0 查询；未修改舵机 EEPROM。接线用户已确认，但供电/转接板/实际 UART 电气链路仍需核实。
- 暴露并修正诊断输出缺陷：原 VOFA TX 环形缓存仅 256 字节，连续状态多行会被丢弃；增至 1024 字节后现场读取完整 STS/SYS/CAM diag/CAM 状态。新增诊断不能只增加打印而忽略承载队列容量。
- USB CDC 为 COM11，可用于 @ 命令。调试期间出现过 COM12，不应固定假设其为 USB CDC；应通过实际响应及 PNP 信息区分串口角色。


## 最终结果与供电补充

- 最终默认 4 分频重新上电后：`frames=329 errors=0 timeout=0 loopmax=7`。用户确认对准明亮目标、移动时画面会跟随变化，摄像头预览现场验收通过，XCAM 暂不需要。
- 最终写入的 CLI 即时校验发生 SWD 读失败；未据此认定写入成功。改用 NORMAL/400 kHz 独立读回首个 128 KB，逐条校验 Intel HEX 校验和并比较所有 119538 个有效数据字节，完全一致，已复位运行。证据 `flash_final_readback.log`、`flash_final_verify.json`，当前目标对应 HEX 的 SHA-256 见 JSON。
- 用户补充转接板标识为 `TTL-BUS RS485-BUS`，舵机当前从通信侧 5V 供电，后续计划在转接板动力端接 7.4V。此标识不足以唯一确定转接板型号，因此不能推定其 MCU/USB 选择开关、跳帽及电源反灌设计。
- 应断电后按转接板实际说明将舵机接 TTL-BUS，使用独立稳压动力电源，动力地与 MCU/适配板地共通；MCU PA2 TX 接适配器 RXD、PA3 RX 接 TXD。不要将动力 7.4V 接到 MCU VCC 或 UART 信号引脚。
- C001 电压资料有版本差异：型号页为 6–7.4V，旧厂家规格 PDF 为 4–7.4V。不能把通信侧 5V 判定为已经证实的故障原因。以实物完整后缀及所附规格为准；后续使用稳压 7.4V 并保证电流能力、测量舵机端电压后，再用只读查询复验。2S 锂电池满电 8.4V，不可仅按标称 7.4V 就直接视作合规输入。
- 资料：[C001 型号与版本差异](https://ftservo.github.io/ftservo-wiki/products/models/st-3215-c001/main/)、[动力与通信分开供电、共地、TTL/RS485 接口区分](https://ftservo.github.io/ftservo-wiki/getting-started/wiring/)、[厂家 C001 规格书副本](https://files.seeedstudio.com/products/Feetech/108090023_STS3215-C001_Datasheet.pdf)。飞特官网页面此次访问超时，Firecrawl 官方页抓取因 DNS 失败；没有将无法访问当成资料缺失。
