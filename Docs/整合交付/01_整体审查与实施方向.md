# 整体成果、方向和步骤复核

## 此前成果的价值与缺口

P1/P2 建立了统一 HAL、UART 角色、LED、按键和诊断；P3 增加 STS 识别、自动波特率和原命令/控制接入。这些可以保留，但覆盖范围偏窄：

- 屏幕还因 OLED 依赖停在工程外，摄像头没有实际初始化和帧缓冲。
- RTC、SD/FatFs、QSPI、USB 例程只列为后续计划，没有工程入口。
- 限位记录仍使用 RAM 后端；复位丢失。
- PWM 文件虽编译，但未进入调度，旧 PA6 与 DCMI 冲突。
- 仅凭单项测试或“P3 完整版”名称，不能判断整个 H743 应用具备厂商例程功能。

因此本轮由按阶段继续追加小诊断，改为先闭合完整的软件依赖和调用图，再针对整合固件做板上验收。

## 现在的实际调用链

```text
Core: MPU/HAL/400MHz system clock/UART1-3
  -> App_Init
       -> LED / Key / HOST protocol
       -> Integration_Init
            -> shared SPI6/QSPI/SDMMC/USB clocks + cycle counter
            -> LCD, RTC, QSPI ID/QE, SD mount, USB CDC
            -> OV5640 (or OV2640) sensor + DCMI/DMA
            -> Bluetooth and independent PWM runtime
       -> STS read-only identification
  -> App_Task
       -> keys / HOST / STS probe or original command-control
       -> integration console / USB / Bluetooth / PWM
       -> snapshot capture -> DMA complete -> 4-row LCD preview strips
       -> LED / display status / optional 10Hz CSV telemetry
```

所有厂商驱动均使用当前工程的 H7 HAL。未把各例程的 `main()`、时钟、UART、LED 或整份旧 HAL 分别拼入工程，避免重复符号与互相抢占外设。

## 厂商示例逐项落地

| 示例 | 整合结果 | 实际入口 |
|---|---|---|
| 【1】LED | 板载和两路外接反馈 | `BoardLed_*` / App |
| 【2】串口打印 | USART1 HOST 队列和诊断日志 | `VendorLog` / VOFA |
| 【3】RTC | LSE、日历、备份域、时间读取/设置 | `@rtc` / `@rtc set ...` |
| 【4】SD 基本读写 | H7 SDMMC1 BSP、原始块 API | `@sd read`；`BSP_SD_ReadBlocks/WriteBlocks` |
| 【5】FatFs | 文件系统、512 字节对齐缓冲 | `@sd retry` / `@sd filetest` |
| 【6】1.54 LCD | 原控制器初始化、文字/绘图和预览 | `@lcd test` / 自动状态页 |
| 【7】QSPI 映射 | MPU 窗口与映射前后数据一致性检查 | `@qspi map` / `unmap` |

| 【11】USB CDC | Type-C 虚拟串口、回显和设备控制台 | USB 枚举后输入 `@help` |

## 实施和验收顺序

软件侧先建立 SDK/资源/内存边界，再将全部模块接入、解决冲突，最后执行完整构建与主机故障模型测试。板上按基础系统、LCD/摄像头、存储/USB、STS 反馈/动作、综合负载的顺序验收。此顺序服务于最终整合，不再把其他设备无限期留在计划中。

最终“工程能运行这些功能”的判断仍要求下载该整合固件、观察实际屏幕与图像、验证外设读写和机械行为。当前已完成软件整合与构建，不能把它写成已经通过实物验收。
